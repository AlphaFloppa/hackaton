# Mesh Routing + Pricing

PHP-модуль для выбора маршрута и расчёта экономики заказа. На входе снимок остатков, сети и загрузки ПВЗ. На выходе маршруты `MESH` и `HUB_TRUNK`, объяснение выбора, список партий для резерва и прогноз для четырёх сторон.

## Запуск

Нужен PHP 8.2+ без внешних пакетов. Для PostgreSQL-адаптера дополнительно нужен `pdo_pgsql`.

```sh
php tests/run.php
php -S 127.0.0.1:8080 -t demo demo/server.php
```

Откройте [демо](http://127.0.0.1:8080/). Для быстрого прогона выберите «Кружка», 2 шт. и «ПВЗ Москва-3». Нажмите «Сравнить схемы», затем «Создать заказ». В карточке откроется маршрут и прогноз экономики. Для межгорода выберите «Куртка» и «ПВЗ СПб-1».

Серверное демо поддерживает создание товаров, приёмку партий, планирование, сборку, выдачу, возврат, логистические инциденты, аналитику и уведомления. Для сквозного прогона создайте товар у продавца, примите партию в одном ПВЗ, затем оформите заказ в другой. Сборка выполняется в ПВЗ отправления, выдача и возврат — в ПВЗ назначения. После возврата товар виден отдельной партией, а вознаграждение за выдачу сторнируется. Кнопка «+10 дней» позволяет проверить начисление хранения и уведомление об остатке старше семи суток.

Инцидент моделирует сбой до отправления из исходного ПВЗ. Сервер пересчитывает путь в обход проблемного плеча. Если обход невозможен, демонстрируется ожидание восстановления с увеличенным сроком. В разделе аналитики ПВЗ показаны операции и платное хранение. В аналитике продавца возвраты исключаются из выручки, а расходы на оказанные услуги сохраняются. Себестоимость можно указать при создании товара. Допущения задаются в `config/model.php`.

При обновлении распакуйте файлы поверх существующего проекта, перезапустите PHP-сервер и обновите страницу. Демо распознаёт заказы и ключи запросов предыдущих версий. Полную историю начислений за время до этого обновления демо восстановить не может, поскольку предыдущие версии хранили текущие статусы и резервы.

HTTP-проверки запускайте с пустым состоянием демо. По умолчанию сервер хранит тестовые заказы в `demo/.state`. Для отдельного прогона укажите новый каталог через `MESH_DEMO_STATE`.

```sh
MESH_DEMO_STATE="$(mktemp -d)" php -S 127.0.0.1:8080 -t demo demo/server.php
```

В другом терминале:

```sh
php tests/http.php http://127.0.0.1:8080/api/v1
```

## Подключение к backend

Подключите `bootstrap.php` или добавьте пространство имён `Mesh\Routing\` с каталогом `src/` в автозагрузку проекта. Контроллеры используют один экземпляр `Router` и одну версию `config/model.php`.

```php
use Mesh\Routing\Router;
use Mesh\Routing\OrderResponse;

$router = new Router(require __DIR__ . '/mesh-routing-pricing/config/model.php');
$plan = $router->plan($input, $snapshot);

// GET /api/v1/frontend/quote
$preview = $plan['quote'];

// POST /api/v1/orders. Внутри транзакции backend с актуальным снимком.
$orderResponse = OrderResponse::create($orderId, $domainStatus, $plan);
$allocations = $plan['selected']['source']['allocations'];
```

| Точка интеграции | Действие backend |
|---|---|
| `GET /api/v1/frontend/quote` | Принять `item_id`, `qty`, `target_pvz_id`, `preference`. Загрузить снимок для продавца и вернуть `quote`. При блокировке вернуть обе причины, `chosen: null` и `block`. |
| `POST /api/v1/orders` | Проверить продавца и `Idempotency-Key`. Под блокировкой остатков и ёмкости перечитать снимок, вызвать тот же `plan()`, зарезервировать партии и место, сохранить заказ и решение в одной транзакции. `NoRoute` преобразовать в HTTP 409, `InvalidArgumentException` из проверки запроса — в 422. |
| `GET /api/v1/orders/{id}` | Проверить доступ продавца и объединить доменные поля заказа с последней сохранённой ревизией маршрута. Статус брать из заказа. |
| `GET /api/v1/frontend/bootstrap` | Существующая интеграция HTML ожидает `seller`, `items`, `pvz` и `orders`. В строки заказов передать `item`, `qty`, `target`, `source_pvz_id`, `status`, `chosen`, `cost`, `hours`, `sla`. См. реализацию в демо. |
| Инцидент | Прочитать заказ и передать в `plan()` его фактическую позицию, недоступные плечи и уже понесённые расходы. При успешном пересчёте использовать `OrderResponse::afterIncident()` и записать новую ревизию. |

### Снимок на входе

| Ключ | Поля |
|---|---|
| `item` | `id`, `kg`, `volume_m3`. Для результата в деньгах добавьте `unit_price_cents`, `unit_cogs_cents`. При отсутствии исходной суммы зависимые показатели будут `null`. |
| `pvzs` | Словарь по ID. `name`, `city_id`, `lat`, `lng`, `capacity_units`, `used_units`, `is_active` (bool). Необязательны `sla_hours_city`, `sla_hours_inter`, `fees` с ключами ставок ПВЗ из конфигурации. |
| `hubs` и `sellers` | Словари по ID. `name`, `city_id`, `lat`, `lng`, `is_active` (по умолчанию true). `sellers` можно опустить при работе только с остатками в ПВЗ. Для хабов из схемы команды подставьте согласованные координаты города или хаба в адаптере. |
| `stock` | Строки запрошенного товара с `batch_id`, `kind` (PVZ или SELLER), `location_id`, `available_qty` после вычета резерва и необязательным `received_at` в ISO 8601 UTC. Модуль может набрать количество из нескольких партий одного пункта. |
| `blocked_edges` | Необязательный список ключей `ВИД|ОТКУДА|КУДА`. Пример `MESH|pvz:ID1|pvz:ID2`. Оба направления блокируются отдельными ключами. |
| `edge_overrides` | Необязательный словарь по ключу ребра с целыми `cost_cents` и/или `minutes`. Применяется к существующим плечам. |
| `storage_days` в запросе | Необязательное количество дней для прогноза. Для публичных ручек можно задавать на сервере. |

`used_units` включает физическую загрузку и действующий входящий резерв. Один и тот же товар учитывается в загрузке один раз. При размещении заказа backend использует `allocations` и `selected.path` для резерва и записи доменных сегментов.

### JSON для фронтенда

У заказа `chosen`, `cost`, `hours`, `segs` описывают **актуальный** маршрут. В `variants.mesh` и `variants.hub` находятся варианты текущего решения. При блокировке вариант содержит `ok: false`, `why`, `segs: []`, `cost: null`, `hours: null`. У заглушек в `segs` установлено `is_stub: true`.

`cost` и `base` возвращаются в рублях, `hours` и `sla` — в часах. `base` фиксирует стоимость хабового варианта при создании. Если хабовый вариант физически возможен, но выходит за SLA, для базы берётся самый быстрый путь через хаб и отмечается `eligible: false` в прогнозе. При отсутствии сравнимого хабового пути `base` равен `null`, в интерфейсе отображается «—».

`order_calcs` — необязательное для клиента расширение. Внутри прогноза поля `*_cents` выражены в копейках, `minutes` — в минутах, `comparison.*.rub` — в рублях, `pct` — в процентах. В первоначальном HTML можно использовать блок `orderFinancials` из демо для отображения прогноза.

### Пересчёт после сбоя

Передайте третьим аргументом `Router::plan()` массив с `kind` (`PVZ`, `SELLER`, `HUB_IN`, `HUB_OUT`), `location_id`, `origin_city_id` для исходного SLA, `spent_cents`, `elapsed_minutes` и при наличии `own_target_reservation`, `completed_segs`. Суммы и время указываются на момент пересчёта, включая уже понесённые последствия инцидента. `own_target_reservation` обозначает место, уже учтённое в `used_units` для данного заказа. Модуль планирует оставшийся путь и добавляет пройденные этапы к ответу.

`afterIncident($previous, $status, $plan, $type, $incidentCostCents, $incidentDelayMinutes)` заменяет верхнеуровневый маршрут, сохраняет исходную `base` и добавляет запись в `incidents`. Последние два аргумента описывают инцидент в карточке, а транспортный итог уже учтён при построении `plan`. При отсутствии допустимого пути доступен `NoRoute` с объяснением для обработки backend.

### PostgreSQL

Примените `migrations/001_mesh_routing.sql` один раз в рамках миграций проекта. Таблицы находятся в схеме `mesh_routing`.

- `DecisionStore::append($orderId, $revision, $response, $plan)` сохраняет ревизию, граф, модель тарифов и прогноз. Вызывайте внутри транзакции доменного заказа с блокировкой его строки и `PDO::ERRMODE_EXCEPTION`.
- `DecisionStore::latest($orderId, $domainStatus)` возвращает `revision` и `response` для карточки. Первая ревизия имеет номер 1. При пересчёте используйте следующий номер.
- Backend владеет статусами, транзакциями остатков и места, идемпотентностью операций, начислениями и фактическими корректировками. Аналитика может агрегировать статус и `chosen` из заказов и брать плановые значения из `order_calcs`.

Проверка на отдельной тестовой БД:

```sh
psql -v ON_ERROR_STOP=1 -d mesh_test -f migrations/001_mesh_routing.sql
MESH_TEST_DSN='pgsql:dbname=mesh_test' php tests/postgres.php
```

## Маршруты и экономика

- Граф направленный. Прямой путь разрешён между ПВЗ одного города в пределах заданной дальности. Через хаб доступны первая миля, обработка, межгород при необходимости и последняя миля. Продавец также может быть источником первой мили при наличии остатков.
- Дейкстра минимизирует стоимость или срок. При ограничении SLA для режима `COST` сохраняются пути с разными соотношениями цены и времени. Приоритет разрешает сравнимые варианты по второй метрике, затем по числу плеч. Все источники с доступным остатком участвуют в поиске.
- Модуль выбирает технически допустимый маршрут по `COST`/`TIME`. Бизнес-условия пилота вычисляются в `pilot_conditions`: маржа и затраты маркетплейса, результат ПВЗ, цена и срок для клиента. Это позволяет отдельно показать, когда выбранный быстрый маршрут экономически оправдан.
- Ставки, пределы и описание потоков денег приведены в [assumptions.md](assumptions.md). В демонстрационном заказе из двух кружек трансфер стоит **24,21 ₽** через mesh и **113,00 ₽** через хаб. При прочих неизменных ставках экономия маркетплейса исчезает на 56-м дне хранения.
